## TDD and evidence rules

For each new behavior: write the smallest meaningful assertion, run its individual `FullyQualifiedName` filter and record the intended observable failure, implement only that behavior, rerun to green, then refactor while green. Where one task lists several cases, repeat this cycle per case/surface rather than accumulating failing tests. Missing symbols or constructor compile errors are scaffolding, not behavioral red: add only the compiling signature/default first, then demonstrate the wrong value, label or state. A rename is a green refactor; a pre-existing passing invariant is regression evidence, not an invented red cycle.

Every implementation task below includes its focused green rerun and green refactor gate. Record red/green commands, actual assertion/observation, and refactor rerun in `specs/062-stats-unit-toggle/validation.md` during implementation. Browser-only gaps require a recorded pre-fix observation and post-fix rerun; if a case already passes through existing seams, record it as a regression and avoid unnecessary production changes. Never claim an unavailable browser/environment case passed.

Use fresh immutable DTO graphs with distinct source amounts, literal conversion anchors or independent decimal expectations, fixed times and stable keys. Settings fakes serialize through the actual configured serializer so reads return fresh objects; isolate GetItem/SetItem faults per test. Dispose providers/resources, restore both cultures in `finally`, restore browser storage/fault injection, use explicit delayed-request signals and observable waits, and avoid sleeps, network/database dependencies or shared mutable fixtures in semantic tests.
