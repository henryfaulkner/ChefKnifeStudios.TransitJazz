# Linode server metrics: built-in Linux dashboards

Use Grafana's [Linux Server integration dashboards](https://gallantpuffin3113.grafana.net/dashboards/f/integration---linux-node/integration-linux-node)
as the replacement for the Azure Container Apps Server Metrics view. The owner selected
built-in dashboards only on 2026-11-14. The custom `transitjazz-linode-server` dashboard was
deleted from Grafana and its JSON removed from this repository.

The installed dashboards are overview (`nodes`), CPU/system (`node-system`), memory
(`node-memory`), filesystem/disks (`node-disk`), network (`node-network`), fleet (`node-fleet`)
and logs (`node-logs`). The logs dashboard was installed by Grafana but log collection is disabled.
Select Prometheus source `grafanacloud-gallantpuffin3113-prom` (UID `grafanacloud-prom`)
and instance `expense-tracker-vm`.

## Collection

Native Alloy was installed on the existing Ubuntu x86-64 VM through Grafana's onboarding
installer. Remote configuration, log collection and integration alerts were turned off.
The bootstrap defines `prometheus.remote_write "metrics_service"` and loads the write token
from a root-only systemd environment file. Preserve that bootstrap and credential; no new
publisher or token is needed for the Linux integration.

[linux-integration.alloy](linux-integration.alloy) is the metrics-only snippet generated by
Grafana's Linux Server integration and supplied during onboarding, with the stable instance
name `expense-tracker-vm` and an explicit 60-second scrape interval. It retains the standard
collectors, metric filter and host-ID enrichment pipeline. It contains no credential values.

The earlier temporary snippet limited collection to the inputs of the removed custom dashboard.
Replace that snippet with the standard snippet, rather than running two exporters. Build a
candidate from `/root/alloy-before-host-metrics.alloy` (the original onboarding bootstrap)
plus `linux-integration.alloy`. Validate the candidate with the installed Alloy binary, preserve
the current configuration as a rollback copy, install the candidate at `/etc/alloy/config.alloy`,
then reload Alloy. Those are separate interactive steps in the operator walkthrough.

Do not append this snippet twice or concatenate it with the earlier custom host snippet.
The native dashboards accept jobs matching `integrations/(node_exporter|unix)`. The standard
snippet explicitly sets `job="integrations/node_exporter"`. The previous Unix exporter supplied
`integrations/unix` in its target labels, overriding the scrape job-name fallback; this is why
the custom dashboard's `transitjazz/linode` selectors did not match the delivered data.

## Verification

The standard snippet was validated on the installed Alloy binary, installed by the owner and
activated with `systemctl reload alloy`. At approximately 14:19-14:20 UTC on 2026-11-14, Alloy
was active and ready, with zero failed remote-write samples and an empty pending queue.
Grafana returned `up=1` and 201 series under `integrations/node_exporter` for `expense-tracker-vm`.
Total memory was 2063577088 bytes and root filesystem size 52212428800 bytes, matching the VM.
The prior `integrations/unix` series age out following the configuration change.

The native overview's saved CPU, memory, disk-capacity and network-receive queries all returned
data over the last 15 minutes at one-minute resolution, using a four-minute rate interval.
The datasource's configured scrape interval is 60 seconds. Observed overview values at
14:20 UTC included about 3.25% CPU usage and 44.41% memory usage. These are sampled values,
not a sustained resource baseline. The owner then confirmed that the native overview's CPU
and memory panels display metrics in Grafana. Setup of the built-in host overview is complete.

After replacing the temporary snippet, check the last 15 minutes in `grafanacloud-prom`:

```promql
up{job="integrations/node_exporter",instance="expense-tracker-vm"}
node_memory_MemTotal_bytes{job="integrations/node_exporter",instance="expense-tracker-vm"}
node_filesystem_size_bytes{job="integrations/node_exporter",instance="expense-tracker-vm",mountpoint="/"}
count({job="integrations/node_exporter",instance="expense-tracker-vm"})
```

Expect `up=1`, about 2063577088 total memory bytes (inspected VM capacity), root filesystem
metrics and a bounded series count. Allow at least two scrapes for rate panels. Open the native
overview and memory/disk/network dashboards to confirm the actual rendered results. Measure
Alloy CPU/memory and Grafana series usage after expanding collection on the shared 2 GB host.

These are whole-VM measurements, including PostgreSQL and other workloads. They do not
replace Azure's app request counts, revision/replica breakdowns or container restart metrics.
The app's 512 MiB / 0.25 CPU limits are separate from host capacity. Existing worker OTLP
metrics and Worker App Metrics remain independent. External availability/freshness alerting
and full host reboot recovery remain separate migration acceptance work.

Keep the stopped Azure dashboard for pre-cutover history until its deliberate retirement.
No application restart, PostgreSQL change or public metrics listener is required for Alloy.
